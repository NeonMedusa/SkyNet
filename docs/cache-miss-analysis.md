# 缓存命中率 0%（`cached=0`）现象分析

> 分析日期：2026-10-07 · 数据来源：`data/logs/*.txt` 全部 14 份日志、1075 次 API 请求
> 结论：**非本程序 bug**；主要由服务端/网关侧行为导致，少数为折叠/压缩的预期代价。

## 现象

状态栏偶尔显示 `缓存 0/338.3k 0%`（正常时 99%），下一轮请求又恢复 ~99%。

## 总体数据（全部日志）

| 指标 | 数值 |
|---|---|
| 总请求数 | 1075 |
| 总输入 tokens | 354,435,679 |
| 总命中 tokens | 343,264,128（**96%**） |
| `cached=0` 事件 | 24 次（2.2%） |
| `cached=0` 贡献的未命中 | 8,827,567 tokens（占全部未命中的 **79%**） |

典型分布：单份日志 miss 率 0%～8%，会话越长、工具循环越密，miss 越多。

## 三种 miss 模式（按出现频率排序）

### 模式 A：服务端/网关侧瞬时失配（主要模式）

特征（多份日志一致）：

- 前一条请求 99% 命中、后一条请求立刻恢复 99%；
- 两条请求间隔仅 5～73 秒，历史仅追加少量内容（Δin=+130 ～ +1700）；
- 期间**无折叠、无压缩、无重启、无工作目录切换**。

```
[1791248502] 响应 3197ms  in=135971  cached=135040 (99%)   ← 正常
[1791248508] 响应 5353ms  in=136520  cached=0     (0%)     ← miss
[1791248515] 响应 6824ms  in=136997  cached=136448 (99%)   ← 立刻恢复
```

**判定**：5 秒内前缀仅追加 ~550 tokens，请求体不可能发生导致全灭的变化。只能是服务端/网关侧：
路由到未持有该前缀缓存的节点、缓存节点瞬时淘汰/抖动，或网关侧请求重组。

**旁证**：所有 `cached` 值均为 64 对齐（1071 条无一例外），说明服务端按 64-token 块计量；
而普通 miss 全部是"整段 0%"（非部分块失配），更像"路由到了空缓存节点"而非"前缀某处变化"
——若前缀真变了，服务端通常给出部分命中（见模式 C 的中间命中率案例）。

### 模式 B：长静默后的失配（预期内）

```
[1791346056] miss（上一条响应在 338s 前）
[1791360918] miss（上一条响应在 14862s ≈ 4 小时前）
```

长工具执行/离开会话后，缓存过期或节点回收 → 下一请求全 miss。属于缓存 TTL 的正常行为。

### 模式 C：折叠/压缩后的前缀变化（设计代价，预期内）

折叠会改写历史中间段（工具输出 → stub），自改动点之后全部失效——这是折叠的已知代价
（见 README「已知限制」）。实测影响有限，重新建立一次缓存后即恢复：

```
折叠 72 条（274KB）→ in=247921 c=41600 (16%)
折叠 44 条（112KB）→ in=212918 c=212864 (99%)   ← 下一发全命中
```

压缩（手动 `/compact`、中途压缩）同理：新前缀第一次请求必然 miss，属语义本身。

## 为什么"经常看到"0%

1. **每轮实时刷新**（usage_update 事件）：每一轮的 0% 都会立即上屏并保留到下一轮结束
   （常见停留 2～8 分钟），比以前回合结束才更新时更显眼；
2. 工具循环密集的会话请求数多（示例会话 110+ 次/段），撞上服务端抖动的概率随之增加；
3. 大输入一 miss 金额代价刺眼（如 338.3k tokens 全价），但频率低（约 1～2 次/小时）。

## 已排除的本程序嫌疑（代码核查）

- 会话路由头稳定：`x-opencode-session` 由 `sessionUuid()` = SHA256("skynet:session:{id}")
  确定性生成，不随重启/加载变化；
- 请求体序列化确定性：messages 无时间戳/随机量；折叠 stub 文本固定；折叠只发生在回合结束；
- 历史快照在回合开始时复制（createStreamJob），之后只追加，不中途乱序；
- miss 与 Δin 无相关（+130 和 +15438 都 miss 过），排除"某类历史变化触发 miss"的规律；
- 请求间无压缩/折叠/重启的事件行时（模式 A），仍出现 miss。

## 建议

- 无需修改代码（显示遵循"纯服务端真实值"原则，语义正确）；
- 如需压低偶发成本：大会话稳定期可手动 `/compact` 一次（缩短前缀，重建一次缓存后稳定）；
- 排查同类问题时：看 `data/logs/` 最新日志中 `[api] 响应 ... cached=0` 行，
  对照前后两条请求的 `in/cached` 与间隔即可归类到上述 A/B/C。

## 2026-10-11 复查补充

- **新观察**：回合结束的折叠（fold）会改写历史前缀 → **下一回合的首个请求几乎必然 miss**，
  命中率取决于“首折位置”（实测 0%～75% 不等；首折点越靠前损失越大，极端时近全灭，
  如 `in=454906 cached=4736 (1%)`）。压缩/重启紧随其后时同理。即：**“每次（回合/会话）
  开始时显示 0%”主要是折叠/压缩的设计代价**，而非网关路由（路由仍是模式 A 的候选）。
- **新增诊断日志（同日）**，用于把每次 miss 定因：
  - `[cache] 请求指纹 bytes=... h4k=... h16k=... h64k=... h256k=... h1m=... h4m=... full=...`
    （固定偏移前缀哈希：跨请求比对即可判断“前缀是否被我们改动”及大致位置）；
  - `[api] 响应 ... endpoint=<x-opencode-endpoint-id>`（网关端点是否漂移）；
  - `[fold] 折叠 N 条（约 XKB）；首折 idx=I（其前约 T tokens，缓存预计自该处失效）`
    （折叠的预期失效点）。
- **判定表（样本积累后按此分类每次 miss）**：

| 请求指纹 vs 上一条 | endpoint | 结论 |
|---|---|---|
| 前缀一致（较长偏移哈希相同） | 相同 | 网关侧（TTL/淘汰/瞬时） |
| 前缀在 X 处变化，且 X 附近有 fold/compact 事件 | 任意 | 我们——折叠/压缩的设计代价（可量化） |
| 前缀在 X 处变化，**无**对应事件 | 任意 | **疑似真 bug（意外漂移）→ 修** |
| — | 变化 | 路由到其他节点 |

- **经济性备注**：折叠省的是“后续请求的输入 token”，代价是“折叠后首个请求的整段重算”。
  工具密集会话里若每回合都折叠，需评估“省”是否大于“赔”（可考虑：更大的折叠批、更低频；
  或仅在接近压缩阈值时折叠）。待样本确认后再定。

## 2026-10-12 结案：实测样本定因（新诊断日志）

样本：一次完整运行（`1791739541.458.txt`）共 **224 个请求**（session 4 + session 12），
非满命中 4 个（3 真 miss + 1 个 98% 恢复），**全部定因**：

| 时刻 | 请求 | 命中 | 定因（证据） |
|---|---|---|---|
| 1:33 | session 4 回合首请求 in=322834 | **1%** | **过渡/冷启动**：上次用该会话是昨天旧构建（无思考回传 → 前缀形状不同）+ 闲置 ~9.5h；下一发 99.9% → 一次性（TTL 与构建换代无法完全分离，均为一次性） |
| 1:46 | 折叠后 in=297012 | **1%** | **我们（折叠设计代价）**：`[fold] 首折 idx=9（其前约 2021 tokens）` + 指纹 `h4k 同 / h16k 异`（漂移点 4–16KB，与折叠点吻合）；端点未变；下一发 99% |
| 3:07 | session 12 回合首请求 in=492105 | **0%** | **网关侧**：`endpoint=deepinfra`（同一次运行中 session 4 全在 `luminal`——节点不同）；此后指纹 h1m 全同 → 非我们漂移；下一发 99%（492672/495429） |
| 其余 220 个请求 | — | ≥99% | 前缀全部 append-only 稳定，**无任何意外漂移** |

**结论**：

1. **无“上下文漂移 bug”**：224 个请求里唯一由本程序造成的前缀变化 = 折叠（1 次，被
   fold 日志 + 请求指纹双重确认）；其余全部稳定。
2. “会话/回合开始 0%”的三类成因均已实测证实：① **折叠**（设计代价，可量化）；
   ② **网关节点切换**（`luminal` vs `deepinfra` 同一次运行内均出现，endpoint 日志直接证实）；
   ③ **冷启动/闲置 TTL/构建升级后的前缀换代**（一次性，立即恢复）。
3. 会话切换（12↔4）本身不引发 miss（前缀不变、同节点时直接 99%）；
   网关对同一 session 有节点亲和（本次样本：session 4 → luminal，session 12 → deepinfra），
   但亲和并非强保证（历史样本中还出现过 novita 等）。
4. 折叠经济性数据点（待决策）：一次折叠省 ~40k tokens/后续请求，赔一次 ~297k 全价重算；
   工具密集会话若每回合都折叠，需评估“省 vs 赔”（选项：更大批/更低频/接近压缩阈值才折）。
5. 诊断日志（`[cache] 请求指纹` / `响应 ... endpoint=` / `[fold] 首折 idx`）继续保留，
   后续如有新的 miss 模式可继续按判定表定因。
