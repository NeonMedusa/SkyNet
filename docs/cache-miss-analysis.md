# 缓存命中率 0%（`cached=0`）现象分析

> 分析日期：2026-10-07 · 数据来源：`data/logs/*.txt` 全部 14 份日志、1075 次 API 请求
> 结论：**非本程序 bug**；主要由服务端/网关侧行为导致，少数为折叠/压缩的预期代价。

## 现象

状态栏偶尔显示 `缓存 0/338.3k 0%`（正常时 99%），下一轮请求又恢复 ~99%。

## 总体数据（全部日志）

| 指标 | 数值 |
|---|---|
| 总请求数 | 1075 |
| 总输入 tokens | 354,435,679 |
| 总命中 tokens | 343,264,128（**96%**） |
| `cached=0` 事件 | 24 次（2.2%） |
| `cached=0` 贡献的未命中 | 8,827,567 tokens（占全部未命中的 **79%**） |

典型分布：单份日志 miss 率 0%～8%，会话越长、工具循环越密，miss 越多。

## 三种 miss 模式（按出现频率排序）

### 模式 A：服务端/网关侧瞬时失配（主要模式）

特征（多份日志一致）：

- 前一条请求 99% 命中、后一条请求立刻恢复 99%；
- 两条请求间隔仅 5～73 秒，历史仅追加少量内容（Δin=+130 ～ +1700）；
- 期间**无折叠、无压缩、无重启、无工作目录切换**。

```
[1791248502] 响应 3197ms  in=135971  cached=135040 (99%)   ← 正常
[1791248508] 响应 5353ms  in=136520  cached=0     (0%)     ← miss
[1791248515] 响应 6824ms  in=136997  cached=136448 (99%)   ← 立刻恢复
```

**判定**：5 秒内前缀仅追加 ~550 tokens，请求体不可能发生导致全灭的变化。只能是服务端/网关侧：
路由到未持有该前缀缓存的节点、缓存节点瞬时淘汰/抖动，或网关侧请求重组。

**旁证**：所有 `cached` 值均为 64 对齐（1071 条无一例外），说明服务端按 64-token 块计量；
而普通 miss 全部是"整段 0%"（非部分块失配），更像"路由到了空缓存节点"而非"前缀某处变化"
——若前缀真变了，服务端通常给出部分命中（见模式 C 的中间命中率案例）。

### 模式 B：长静默后的失配（预期内）

```
[1791346056] miss（上一条响应在 338s 前）
[1791360918] miss（上一条响应在 14862s ≈ 4 小时前）
```

长工具执行/离开会话后，缓存过期或节点回收 → 下一请求全 miss。属于缓存 TTL 的正常行为。

### 模式 C：折叠/压缩后的前缀变化（设计代价，预期内）

折叠会改写历史中间段（工具输出 → stub），自改动点之后全部失效——这是折叠的已知代价
（见 README「已知限制」）。实测影响有限，重新建立一次缓存后即恢复：

```
折叠 72 条（274KB）→ in=247921 c=41600 (16%)
折叠 44 条（112KB）→ in=212918 c=212864 (99%)   ← 下一发全命中
```

压缩（手动 `/compact`、中途压缩）同理：新前缀第一次请求必然 miss，属语义本身。

## 为什么"经常看到"0%

1. **每轮实时刷新**（usage_update 事件）：每一轮的 0% 都会立即上屏并保留到下一轮结束
   （常见停留 2～8 分钟），比以前回合结束才更新时更显眼；
2. 工具循环密集的会话请求数多（示例会话 110+ 次/段），撞上服务端抖动的概率随之增加；
3. 大输入一 miss 金额代价刺眼（如 338.3k tokens 全价），但频率低（约 1～2 次/小时）。

## 已排除的本程序嫌疑（代码核查）

- 会话路由头稳定：`x-opencode-session` 由 `sessionUuid()` = SHA256("skynet:session:{id}")
  确定性生成，不随重启/加载变化；
- 请求体序列化确定性：messages 无时间戳/随机量；折叠 stub 文本固定；折叠只发生在回合结束；
- 历史快照在回合开始时复制（createStreamJob），之后只追加，不中途乱序；
- miss 与 Δin 无相关（+130 和 +15438 都 miss 过），排除"某类历史变化触发 miss"的规律；
- 请求间无压缩/折叠/重启的事件行时（模式 A），仍出现 miss。

## 建议

- 无需修改代码（显示遵循"纯服务端真实值"原则，语义正确）；
- 如需压低偶发成本：大会话稳定期可手动 `/compact` 一次（缩短前缀，重建一次缓存后稳定）；
- 排查同类问题时：看 `data/logs/` 最新日志中 `[api] 响应 ... cached=0` 行，
  对照前后两条请求的 `in/cached` 与间隔即可归类到上述 A/B/C。
