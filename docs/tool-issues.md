# 工具问题日志（AI 维护）

> **这是什么**：AI 在使用自己的工具（read / write / edit / bash / grep / find / ls）过程中，
> **亲身遇到**的问题、摩擦与改进机会的流水账。目的不是立刻修，而是**沉淀证据**——
> 等有空时由人类 + AI 一起评估，按价值排期改进。
>
> **维护者：AI**（每次任务里若遇到下列情况，**顺手记一条**，不要专门为记录中断主任务）。
> 人类只读、不写；排期与取舍由人类决定。

## 记录规则（AI 必读）

**记什么**（按价值排序）：
1. **Bug**：工具行为与文档/预期不符，或产生了错误结果（含"差点出错但被拦住"）；
2. **无效/低价值提示**：诊断信息没帮我定位问题、或者啰嗦到浪费 token；
3. **诊断不完善**：失败时信息不足，导致我多花 1-2 轮往返去猜；
4. **改进机会**：我不得不改用别的工具/写 Python 脚本绕过的场景（**记下绕法**）；
5. **正面反馈**：某个改动**确实**解决了问题（简短记一条，便于人类判断价值）。

**怎么记**（每条 2-5 行，别写成散文）：
- **日期 + 一句话标题**；
- **场景**：我做了什么、期望什么、实际什么（**贴关键证据**：错误原文 / 命令 / 文件片段，短）；
- **影响**：多花了几轮往返 / 产生了错误结果 / 差点写坏文件；
- **可能的修法**（可选，一句话）；
- **状态**：`open` / `fixed(提交号)` / `wontfix(原因)`。

**不要记**：我自己手滑写错参数（那是我的问题，除非工具本可以拦住）；
一次性环境问题（mock 没启动之类）；已经在 `docs/development.md` 2.5/2.6 等章节
记录过的工具演进设想（那边是"设计层面"，这里只记"使用体验"）。

### 2026-09-25 · edit：行锚定拒绝后的诊断可以更直白

- **场景**：文件行 `    keep   indented();`，我写 `    indented();`（4 空格缩进）。
  精确失败 → 放宽链 `inner_ws` 能命中行中部的 `indented();`，但被行锚定拒绝 →
  最终报"逐行不匹配"诊断。行为**正确**（没写出垃圾），但诊断没说**为什么**放宽也没成。
- **影响**：我第一反应是"放宽链没生效？"，多花了 1 轮排查。
- **可能的修法**：行锚定拒绝时，在诊断里加一句"a loose match exists at line N but is not
  line-anchored (something non-whitespace precedes it) - extend old_text to include it"。
- **状态**：open（低优先：这是罕见场景，且当前诊断已能定位行号）

### 2026-09-25 · edit：子串语义让"带缩进的 old_text"总能精确命中，放宽链少有机会触发

- **场景**：多次实测"缩进差异"时，我写的 `    child();`（4 空格）总能精确匹配到
  `        child();`（8 空格）的**后半段**——因为 8 个空格里取后 4 个正好等于我的 4 个。
- **影响**：无（结果正确）。但**说明放宽链的 `indentation-flexible` 级别在实际使用中
  很少被触发**——它的价值主要在"old_text 首尾不是纯内容"的场景。
- **可能的修法**：无需改；记录下来避免以后误以为该级别没用。
- **状态**：open（观察项，非问题）

### 2026-09-25 · edit：多重差异叠加时产生"行中间部分子串"替换（**fixed**）

- **场景**：文件行 `        \\ TABLE x (`（8 空格 + 2 反斜杠），我写 `  \ TABLE x (`。
  放宽链 `indentation-flexible` 归一化后，我的文本命中文件行的**后半段**，
  替换后产生 `        \\  \\ TABLE y (` —— **垃圾残留**。
- **影响**：**差点写坏文件**（实测发现；当时是真实文件的话就出错了）。
- **修法**：新增 `lineAnchored` 保护——放宽匹配区间两侧到行边界之间只能是空白，
  否则拒绝（宁可报错）。已实现 + 单测覆盖。
- **状态**：fixed（本轮改动，随"分级容错匹配"一起提交）

### 2026-09-25 · edit：反斜杠层数 / 行尾空白 / 缩进差异导致必然失败（**fixed**）

- **场景**：我写 `\CREATE`（1 个反斜杠）而文件是 `\\CREATE`（2 个）；或行尾空白差异。
  这些以前**必然失败**，我只能改用 Python 脚本（`io.open(...).read().replace(...)`）绕过。
- **影响**：每遇到一次多花 2-3 轮往返（写脚本、跑、清理），且脚本比 edit 调用更重。
- **修法**：分级容错匹配链（4 级，对齐 opencode）。实测三个级别均按预期工作，
  响应附短标记 `(matched loosely: <level>)`。
- **状态**：fixed（本轮改动）

### 2026-09-25 · edit：失败诊断只有"首行近似位置"，信息量低（**fixed**）

- **场景**：多行 `old_text` 失败时，旧诊断只说"首行在第 N 行"，不说**哪一行开始不对**。
- **影响**：我得 read/grep 反复对比，1-2 轮往返。
- **修法**：逐行比对诊断（定位首个不匹配行 + 期望 vs 实际 + 空白/转义层数加注）。
  实测对反斜杠差异与行首空白差异**一次命中**。
- **状态**：fixed（本轮改动）

### 2026-09-25 · bash：长输出截断后没有"如何取回"的指引（**已核实：不成立**）

- **场景**：我怀疑 `bash` 输出被截断后没有取回完整输出的提示。
- **核实结果**：**错怪了**——代码里已有 `Full output saved to: <路径>` 提示 + 启动时清理过期
  临时文件（`cleanupStaleBashTempFiles`），且有专门测试覆盖（"bash 截断时全文落临时文件，
  可用 read 续看，无需重跑"）。
- **教训（对 AI 自己）**：记 issue 前先 grep 一下代码，别把"我没注意到"当成"工具没做"。
- **状态**：wontfix（非问题）
